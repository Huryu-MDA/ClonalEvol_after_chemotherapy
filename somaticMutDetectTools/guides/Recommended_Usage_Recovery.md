# Recommended Usage Style and Failure Recovery

This section outlines the preferred approach for using this modular pipeline in LSF environments, particularly where compute or I/O issues may occasionally cause job failures.

---

## 🧭 Usage Philosophy

Due to the unpredictable behavior of HPC environments (e.g., silent node failures, I/O hiccups, scratch quota overruns), this pipeline is **intentionally modular and checkpointed**.

Rather than packing everything into a single automated system, each major step should be run and verified independently.

---

## ✅ Usage Strategy

1. **Run each pipeline phase separately:**
   - `Mu2_1stCall` → `Mu2_2ndCall` → `VCF_FilterTag`
   - Submit jobs with descriptive names and store `JobID_*` files

2. **Always check `.log` and `.err` files generated by `bsub`:**
   - Use `bjobs`, `bpeek`, or check output in corresponding folders
   - Ensure no `SegFault`, `OutOfMemory`, or truncated output

3. **Use `WaitSignalMaker.sh`** to coordinate downstream job dependencies based on job ID logs

4. **Keep intermediate results:**
   - If a sample fails, you can rerun that part only (e.g., one tag or one chromosome)

---

## 🔄 Recovery from Failure

If any script fails or produces incomplete output:

- ✅ Identify failed jobs via `bjobs` or by inspecting `JobID_*.txt` files
- ✅ Inspect `.err` and `.log` files under the relevant output directories
- ✅ Rerun only the failed part:
  - Re-submit a failed chromosome
  - Re-run tagging on one sample
  - Re-call one step using known good inputs

---

## 🔒 Stability Tips

- Run long jobs with `BsubL` and memory-aware jobs with `BsubM`
- Prefer real paths (`realpath`) for I/O file references
- Keep final matrices and VCFs timestamped (via `timeID`) to avoid overwriting

---

This approach ensures reliability, debuggability, and robustness in environments where “a grain of sand” can bring down an entire job batch.
